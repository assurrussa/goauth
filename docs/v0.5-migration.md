# Migrating v0.4.1 to v0.5.0

v0.5.0 is an unpublished candidate. It preserves schema version 3 and existing
auth rows. Keep the immutable baseline migrations; do not reset production data.

## OIDC and HTTP adapter review corrections

- Public clients using `none` always require S256 PKCE, even when
  `RequirePKCE=false`. Confidential basic/post clients may omit a challenge when
  that flag is false; any supplied challenge requires S256. Method-only metadata
  and unsupported methods are rejected.
- PKCE verifiers must contain 43-128 ASCII unreserved characters. Short values,
  whitespace and reserved/non-ASCII characters are rejected without normalization.
  S256 challenges must encode exactly 32 bytes as canonical unpadded base64url.
- Provider JWKS rejects incompatible RSA signing metadata, including blank key
  IDs, encryption usage or a non-RS256 algorithm. Omitted `use`/`alg` remains
  supported; third-party verifier sets still filter incompatible entries.
- `provider.Options.TokenEndpointAuthMethods` is both the discovery list and the
  runtime allowlist. Nil keeps defaults; explicitly empty lists, blank values
  and unknown methods fail construction. Unknown client/request methods are
  rejected rather than silently replaced by defaults.
- Provider access tokens require RS256, issuer, expiration and issued-at claims;
  expired/future-issued tokens are rejected using the configured clock.
- OIDC RSA signing/verification keys below 2048 bits or with malformed N/E are
  rejected, including custom stores and JWK inputs. Signing validates the private
  key and matching public key.
- Persistent registries may supply `provider.Options.ClientSecretVerifier`.
  Set an explicit confidential-client auth method when `Client.Secret` is absent.
  A nil interface preserves legacy static secrets; a typed nil function returns an
  error. Verifier errors never trigger fallback.
- Custom Fiber Runtime implementations replace `VerifyAccessToken` with
  `AuthenticateSession` and `VerifyJWT`. Existing root/PostgreSQL Runtime values
  already satisfy the updated interface. The supported Fiber handler subset is
  listed in the README; auth bodies above 1 MiB return 413 before Runtime calls.
- Both HTTP adapters map disabled delivery to 501
  `notification_delivery_disabled` instead of an internal error.
- Suspect RBAC cache reads fall back to PostgreSQL. Successful invalidation
  restores a transient failure; uncertain write commits keep the wrapper bypassed.
  Each post-commit invalidation has a two-second deadline, including lock waits;
  custom invalidators must honor cancellation. Timeout preserves committed writes
  and bypasses suspect cache reads until a fresh successful invalidation.
- `rbac.Service.Snapshot` through PostgreSQL rejects a managed auth transaction
  with `rbac.ErrSnapshotTransactionUnsupported`. Call it outside that context to
  retain its standalone repeatable-read, read-only snapshot guarantee. A read-only
  snapshot commit failure retains typed error classification without bypassing
  the authorization cache.
- Make uses standard Go cache paths by default. Hosts that require shared caches
  set `GO_SHARED_CACHE_ROOT` or individual cache variables explicitly.

## Email reauthentication and browser logout follow-up

The net/http email-change handler now requires `currentPassword` alongside
`email` and uses `RequestEmailChangeWithPassword(PasswordEmailChangeRequest)`.
The optional `nethttp.PasswordEmailChangeRuntime` capability keeps existing
Runtime implementations source compatible, but the handler fails closed with
503 when that capability is absent. It never falls back to subject-ID-only
issuance. The root `RequestEmailChange` remains a trusted API for hosts that
perform their own recent authentication, including SSO; it is not a public
HTTP reauthentication shortcut.

Password and email changes share the existing subject-keyed `password_change`
attempt bucket. The verified account snapshot is rechecked under the subject
lock. The existing `email_changed` notification now goes to the previous mailbox,
not the replacement address; templates must not imply that its recipient owns
the new address. New-address confirmation remains unchanged.

PostgreSQL Runtime construction rejects non-email identifier resolvers before
connecting or migrating. Custom identifier schemes require direct root assembly
with a store that supports them; silently returning "account not found" is no
longer accepted as configuration validation.

The runnable browser example coordinates refresh and logout in one Web Lock.
Successful invalidation blocks queued refresh until a new login. A lost response
is not treated as confirmed revocation, and a failed refresh is not retried
blindly. See [follow-up contracts and validation](reauth-email-logout.md).
No database migration, schema reset, new dependency or release tag is involved.

## Runtime and store assembly

`postgres.NewRuntime` supplies `AuthTransaction`, the mandatory local audit
store and the native encrypted queue through managed notification assembly.
It rejects custom `EventSink`, `AuditSink` and `AuthTransaction` overrides before
connecting to the database or migrating, including when no managed sender is
configured. PostgreSQL hosts provide `NotificationSender` for delivery through
the queue; an external event sink cannot participate merely by receiving the
PostgreSQL callback context. Custom enlisted event sinks require direct root
assembly with `Config.AuthTransaction` and `Config.AuditSink`. All participating
stores, audit writes and encrypted enqueue must use the callback context and the
same transaction; a passthrough callback is not a valid implementation.
`Config.NotificationTransaction` is retired and returns a configuration error.
`Store.InNotificationTransaction` remains a deprecated entry point to the full
PostgreSQL transaction for source compatibility.

Custom stores implement `LockAccount` and `PeekRefresh`. Lock the canonical
subject before child rows, reject creation of a session from a stale security
version, and revalidate the authenticated refresh snapshot during rotation.
`PeekRefresh` never consumes a token or revokes a session. `RotateRefresh` must
process an authenticated replay even when no next token was prepared.
Logout-all advances security version; registration and external login commit
account/link/session writes together. Mandatory audit failure rolls back the
associated writes. Wrong-code attempts and replay revocation commit before their
business error is returned.

Hashing, membership checks, claims enrichment and JWT preparation run before
write transactions. Hooks should return promptly and must not assume a newly
registered account already exists in storage. Host membership checks are a
point-in-time decision; hosts own synchronization of their membership data.
`Register`, `Login` and `LoginExternal` reject a prepared token pair that expires
during claims preparation or session storage. `ErrExpiredToken` rolls back the
new session and any account or identity link created with it. Access-token
expiry is checked at JWT second precision before the transaction commits.
Refresh replacement expiry is computed from the final rotation time and capped
by the absolute session expiry. If the prepared access JWT has expired before
rotation finishes, or the replacement expires during rotation, `Refresh` returns
`ErrExpiredToken` and rolls back consumption and replacement together. Its JWT
`exp` boundary uses second precision. An authenticated replay still commits
family/session revocation and audit before returning `ErrRefreshReplay`.
Custom renderers/audit implementations must not perform irreversible external
actions from a transaction callback. Send notifications through the worker after
commit. Keep the native queue; no message bus or external outbox is required.

## Authentication defaults and retries

Custom `PasswordHasher.VerifyPassword` implementations can keep their native
mismatch errors, including wrapped or joined errors. `Login` and
`VerifyCredential` return `ErrInvalidCredentials` for these mismatches;
`ChangePassword` rejects an incorrect current password and accepts a different
replacement. To report an operational verification failure instead, wrap or
join `ErrPasswordVerificationUnavailable` with the underlying cause. Runtime
also preserves `ErrPasswordHashOverloaded`, `context.Canceled` and
`context.DeadlineExceeded`. `HashPassword` failures always retain their cause.
Unmarked verification errors keep the legacy mismatch semantics; custom hashers
that use a remote service must explicitly mark its outages.
Both HTTP adapters map `ErrPasswordVerificationUnavailable` to 503
`authentication_unavailable` with a fixed message and no dependency details.
`ErrOperationOutcomeUnknown` retains precedence if both markers are present.

Use `AuthenticateSession` to check current session, subject, security version and
admin/custom realm membership. `VerifyJWT` performs offline verification only;
revocation may remain invisible until access-token expiry (at most five minutes).
`VerifyAccessToken(ctx, token, introspect)` remains deprecated. Both HTTP adapters
default to current-session authentication; `OfflineJWT: true` explicitly opts out.
The old Fiber `Introspect` field is retained, but false no longer disables checks.

During a database outage, current-session authentication fails closed. Do not
fallback automatically to offline verification. Transient preparation failures
leave the existing refresh token usable. Once rotation may have committed,
retrying the same refresh token can revoke its family: strict replay detection
has no grace period. Serialize refresh across browser tabs. If transport fails
after submission or `ErrOperationOutcomeUnknown` is returned, discard local
tokens and authenticate again; never automatically replay the mutation.
HTTP adapters map an uncertain outcome to status 503 and
`operation_outcome_unknown`. A known callback error rolls back; commit I/O errors
may leave the server result unknown even though the caller received an error.

An error containing `ErrOperationOutcomeUnknown` keeps the
`operation_outcome_unknown` response even when it also wraps cancellation,
deadline, overload or throttling causes. Both HTTP adapters omit `Retry-After`
for that result. A plain cancellation or deadline without an unknown commit
outcome still returns `authentication_unavailable`.

The net/http account handlers return explicit client outcomes: incorrect current
password, unchanged password and unchanged email use 422 with
`current_password_invalid`, `password_unchanged` and `email_change_same_value`.
A concurrent password change uses 409 `password_change_conflict`; missing pending
email change uses 404 `email_change_not_found`. A wrong current password does not
mean the authenticated session is invalid. Unexpected failures retain a redacted
500 `internal_error` response.

Both HTTP adapters return 400 `invalid_realm` for a malformed login realm and
400 `realm_not_registered` for a valid realm name that the Runtime has not
registered. These responses do not echo the supplied realm or set `Retry-After`.
Omitting the realm still selects `user`; membership and email-verification
denials retain their 403 responses.

## External identities and verifier

Pass only identity claims validated by a trusted provider; never bind client JSON
directly to `ExternalIdentity`. Issuer and subject are exact protocol identifiers.
An issuer ending in `/` and one without it are different. Existing links resolve
without an email claim. Provisioning a new account requires an email.

`AutoLinkVerifiedEmailIssuers` controls new verified-email links:

- nil or `["*"]`: all issuers the host has already chosen to trust;
- an explicitly empty slice: automatic linking disabled;
- exact issuer strings: only those issuers;
- `*` mixed with other values: configuration error.

Both external and local email must still be verified and equal after email
normalization. Changing the policy does not invalidate existing links or sessions.
No production SSO accounts requiring legacy relinking were reported for this
migration. Other consumers must inventory historical links themselves: values
lost to old normalization cannot be reconstructed safely from stored rows.

The OIDC verifier requires `exp`, nonempty `sub`, exact issuer agreement and its
existing signature/audience/time checks. HTTP defaults are a five-second deadline,
a one-MiB response limit, HTTPS and no redirects. `AllowInsecureHTTP` is an explicit
local-development option. `DiscoveryURL` overrides only the fetch location, never
issuer identity. Concurrent JWKS fetches are coalesced; unknown-key forced refresh
is limited to once per 30 seconds. Failed refreshes retain valid cached keys.
Canceling a caller stops its wait without canceling the shared fetch. The whole
fetch, including discovery, is bounded by `HTTPTimeout`; a context already
canceled before refresh does not spend the unknown-key cooldown.
This release makes no OIDC conformance claim.

## Passwords, keys and operational boundaries

A partial `PasswordPolicy` inherits the built-in common-password blocklist.
Use `DisableBlocklist: true` only for an intentional override. The minimum remains
eight Unicode code points. No automatic rehash or global Argon2 limiter is added.

Rotate JWT, token-HMAC and notification-AEAD keys independently with distinct
material and version IDs. Deploy readers accepting old and new keys before
switching the active writer. Retain old JWT keys through access-token expiry,
HMAC keys through the lifetime of affected refresh/reset/challenge records, and
AEAD keys until queued encrypted deliveries are drained or expire. Missing AEAD
keys block delivery: alert on the safe worker signal without logging plaintext.
Restore the old read key to recover; deleting a key is not a normal revocation API.

`postgres.Down` still requires explicit confirmation and affects only owned auth
objects. Generic `roles`, `permissions`, `role_permissions` and `role_hierarchy`
belong to the host and survive reset. Foreign-key dependencies prevent unsafe
partial reset. Use the runnable net/http example for cookie/CSRF/browser wiring;
the root library owns no HTTP cookies or UI policy.

## Password resource and OIDC profiles

All password inputs are bounded before the configured hasher is invoked. Runtime
admission defaults to four concurrent hash/verify operations, with immediate
`ErrPasswordHashOverloaded` when saturated. Legacy login checks retain the
existing credential semantics; new-secret policy still applies to changes.
Infrastructure failures retain their cause and are not invalid-credential results.

Every returned access/refresh expiry is capped by the canonical absolute session
expiry. HTTP hosts cap persistent cookies to those returned bounds.

The OIDC verifier's default embedded profile requires exact `token_use=access`.
ZITADEL JWT access validation requires explicitly selecting
`verifier.AccessTokenProfileZITADEL`; the profile rejects ID/logout-only claims
and retains signature, issuer, audience, time and discovery protections. This
is an explicit protocol subset, not generic provider conformance.

## Additional review corrections

Email operations recheck active subject state under the canonical lock. Pending
email changes and outstanding verification challenges are invalidated in the
same transaction as password/reset/email/status/logout-all security-version
changes. Custom stores must implement that invalidation. PostgreSQL evaluates
one-time-secret expiry after subject and record lock acquisition, not from a
stale time sampled before the wait. No schema-version change is required.

Password-change attempts use their own subject-keyed bucket with the configured
login window and limit. Both adapters preserve typed retry deadlines; Fiber auth
responses now explicitly prohibit caching. `LogoutAll` reports only newly revoked
sessions, while retaining its security-version advancement.

`oidc.AuthorizationCode.SecurityVersion` is now required by the provider. Custom
code stores must persist and return it unchanged. Built-in Redis JSON storage
already round-trips it without a database migration. Authorization rejects stale
host authentication snapshots, and exchange rejects inactive/wrong subjects,
changed security versions and codes without a version. In-flight codes written
by an older binary therefore require starting authorization again; do not fill
their missing version from the current account. Deploy code-store support and
provider writers/readers together, and do not roll back to a reader that ignores
this binding. No account, session or production schema reset is needed.

A security change completed between code issuance and exchange invalidates that
grant. This does not claim a distributed transaction across Redis, subject reads,
JWT signing and response delivery. Hosts still own current authentication and
canonical claims resolution.

The verifier tolerates mixed JWKS by filtering RS256 signing candidates, rejects
ambiguous key IDs, backs off failed fetches, and returns the configured matched
audience in `VerifiedAccessToken.Audience`. OIDC refresh-store commit I/O failures
preserve `ErrOperationOutcomeUnknown`; the no-automatic-replay policy applies.

See [review corrections and evidence validation](review-corrections.md) for the
added regressions, the distinct full public-preview evidence gate, and checks
that have not been performed.
