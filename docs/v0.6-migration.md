# Upgrading to GoAuth v0.6

`v0.6.0` is the selected next minor release from schema-8 master. This document
describes its upgrade contract, not evidence that the tag has been published or
that any deployed host has been upgraded. Check the repository's tag and release
notes for the tested source, completed gates and public availability.

The published starting point is `v0.5.1`
(`0862228fd3d3e33d5cc46ed7fc92136df247bdbe`, schema 3). This is the full intervening
feature and security release, not a two-fix backport. Go 1.27 is required; the
repository declares toolchain Go 1.27.1. The module path and supported import
manifest remain unchanged.

## Changes to review before adopting

- Privileged local identities: import/create email-less identities, explicit
  opt-in legacy password input compatibility, primary custom-login lookup and
  rename, and trusted operator password replacement. These are privileged host
  APIs, not public HTTP endpoints or permission to bypass host authorization.
  Existing browser/admin email and membership requirements remain in place.
  [Local identity contracts](local-identities.md).
- Owned outermost auth transactions and runtime-bound credential preparation
  support host operations that release a credential or response only after a
  confirmed commit. An unknown commit outcome is not permission to blindly
  retry or expose provisional output. [Transaction contract](owned-auth-transactions.md).
- Credential verification gets a separate bounded admission policy. Its zero
  value inherits the resolved login policy; it does not disable throttling.
  [Credential admission](credential-admission.md).
- Managed notifications distinguish positively known sender rejection from
  retryable or unknown outcomes and expose bounded encrypted-envelope expiry.
  [Notification outcomes](notification-outcomes.md).
- Terminal subject retirement preserves a durable disabled tombstone, advances
  security state atomically and makes login reuse an explicit privileged host
  decision. It is not an ordinary reversible account disable.
  [Retirement contract](subject-retirement.md).
- Bounded rate-event cleanup and strict session-bound OIDC state cleanup give
  hosts focused maintenance paths. Hosts still choose cadence and timeouts.
  [Rate-event maintenance](rate-event-maintenance.md).
- The explicit session-bound OIDC profile ties issuance and UserInfo to a live
  host session, project/client/grant admission and fixed absolute deadlines.
  It adds no end-session endpoint or automatic downstream logout delivery.
  [Session-bound OIDC](session-bound-oidc.md).
- Canonical refresh cleanup preserves replay evidence while a family can remain
  live; Login concurrent with email confirmation can safely reprepare its token
  pair. [Session security fixes](session-security-fixes.md).

## Source and behavior compatibility

Existing required `RuntimeStore` methods and the legacy provider entry point
remain available; new privileged capabilities are optional interfaces. Public
records/configuration gain fields. Prefer keyed struct literals and rerun the
public consumer and the host's own compilation/tests rather than assuming a
minor version is source-compatible with every custom store.

Review these intentional behavioral contracts even when compilation succeeds:

1. Legacy `OIDCRefreshTokenStore.Get` is read-only. A consumed token returns an
   inactive snapshot via `RefreshToken.RevokedAt`; that value does not prove a
   persisted family revocation. Callers relying on Get to revoke/audit must use
   authenticated mutation. The legacy provider authenticates the exact owner
   before Revoke; direct adapter Revoke remains a trusted storage API.
2. A custom `CreateSession` must reject a scope inconsistent with locked email
   verification state. During the narrow Login/confirmation race,
   `ClaimsEnricher` can run twice for one Login. Preparation hooks must tolerate
   this; no discarded token/session pair may escape or be persisted.
3. `Runtime.Cleanup` is successive maintenance transactions. Earlier phases can
   commit before a later failure; an error is not global rollback. Canonical
   refresh-family deletion is not row-count bounded. Keep host timeouts/cadence.
4. Already-deleted refresh history cannot be reconstructed. Old tokens remain
   invalid, but lost evidence cannot attribute replay to a still-live family.
   Whether to revoke pre-existing sessions is a separate rollout decision.
5. Legacy password compatibility remains off by default. Enabling it requires
   the documented profile preflight and capacity planning for two sequential
   Argon2 jobs within one hash-budget slot. It does not widen strict records.

## Database upgrade: schema 3 to schema 8

Run the supported `postgres.Migrate`, or an explicitly authorized host
`AutoMigrate` startup path. Do not copy SQL fragments, edit migration history,
reset canonical auth state or drop host projections. Prior migration bytes and
checksums stay frozen.

| Schema | Addition | Operational consideration |
| --- | --- | --- |
| 4 | Local-credential password input policy | Existing credentials keep strict defaults and their hashes/identities. |
| 5 | Notification expiry index; verification of the existing expiry constraint | Index creation uses the normal migration transaction; plan for retained-history size and lock time. |
| 6 | Subject retirement tombstone and validated disabled-only fence | Existing subjects start unretired; later tombstones must survive rollback/restore. |
| 7 | Rate-event cleanup index | Preserve earlier checksums and plan index-build/lock time. |
| 8 | Session-bound OIDC requests, codes and family/session bindings | Use coordinated migration/restart; mixed older writers are unsupported. |

Older binaries reject future schemas. Stop/drain old writers before migrating,
including workers and maintenance processes, and enable strict readiness before
serving with new binaries. Preserve canonical subject IDs, identifiers, password
hashes/input policies, security versions, memberships/grants, host mappings and
encryption/signing/refresh key material. Do not invent a second identity source.

### Pre-production rehearsal and release evidence

Use only disposable databases and synthetic data for the release rehearsal.
Keep detailed evidence outside the clean source checkout and omit secrets from
logs, screenshots and public release notes.

1. Record the exact candidate SHA and baseline tag. Generate a populated schema-3
   fixture with the actual `v0.5.1` runtime, including credentials, sessions and
   consumed/current refresh tokens plus a pending encrypted notification. Save a
   backup and verify it restores before upgrading; retain the synthetic keys.
2. Upgrade a copy to schema 8 and verify canonical IDs, hashes, versions,
   identifiers, grants and host mapping rows are preserved. Require clean
   `VerifySchema`, idempotent migration, successful old-password login, current
   session/refresh continuity and correct consumed-token replay denial/revocation.
   Check new schema invariants and confirm an old binary refuses the new schema.
3. Take a schema-8 backup and restore it into another isolated database. Recheck
   schema, decryption, live-session behavior, replay evidence and retirement
   tombstones. Include strict session-bound OIDC state; a fresh empty install is
   not an upgrade or rollback rehearsal.
4. Run the declared candidate gates at the frozen SHA. Existing exact-source CI
   can supply only its recorded constituents. Explicitly run real dump/restore
   and real Chromium/HTTPS acceptance, which the CI workflow does not execute.
   Also enable the native retirement and session-bound backup tests with
   `GOAUTH_TEST_RETIREMENT_BACKUP=1` and `GOAUTH_TEST_SESSION_BACKUP=1`.
5. In disposable AuthHub and GoAdmin checkouts, resolve the exact candidate GoAuth
   commit/version without local replacements and record both host source commits
   and complete resolved module graphs. Before tagging, an exact commit may
   resolve as a Go pseudo-version; record its full SHA. Do not update unrelated
   dependencies or infer deployment from these temporary acceptance changes.
6. Run each host's relevant format/lint/test/migration checks. AuthHub acceptance
   must include login, authorization-code/PKCE issuance, refresh, UserInfo,
   membership/grant denial, central logout and strict readiness against a real
   disposable PostgreSQL database. GoAdmin acceptance must include existing-user
   admin login, membership/permission boundaries, profile/session behavior,
   refresh/replay/logout and a restart with preserved state. A synthetic library
   consumer does not replace either host check. Report skipped/manual flows.

The repository's migration suite already tests populated schema 3→8 row/history
preservation. The actual-tag fixture and host rehearsals above additionally
establish functional behavior across independently built old/new runtimes.
Passing them is required evidence, not an assertion made by this guide.

## Rollback without reviving revoked access

Prepare a known-good **schema-8-compatible** application binary and host
configuration before allowing writes after the upgrade. An application-only
rollback to `v0.5.1` against schema 8 is unsupported. Never lower the schema
marker, clear tombstones or use `postgres.Down` on production data.

A schema-3 snapshot can reverse an isolated rehearsal, or an aborted upgrade only
when it is a consistent auth/host snapshot captured with writers quiesced and
there have been no auth/host writes since that snapshot. It is not a general
post-rollout rollback:
restoring it after revocations, password changes, retirements or grant changes can
revive access or lose identity mappings. After such writes, use a compatible
schema-8 backup and reconcile subsequent security and host state, or roll forward
to a corrected schema-8-compatible build. Keep backups and required keys under
the operator's normal access/retention controls; never publish them.

No production migration, deployment, session revocation, key change or host
dependency publication is authorized or performed by selecting this release.
Those operational decisions and the recovery point belong to a separate rollout.

## Publication sequence

After mandatory gates and independent review pass, create the unused `v0.6.0`
tag at the frozen source. Never move an existing tag. From its clean checkout,
run `make public-module-check VERSION=v0.6.0` with fresh anonymous caches,
public proxy/checksum verification and no replacement. Publish release notes
only after this exact-tag public consumer succeeds. Include the source SHA,
migration/rollback warning, actual host versions and evidence boundaries.

The full aggregate command for published release readiness is
`make release-readiness VERSION=v0.6.0`, with the disposable services and browser
tools available. The public-module check alone proves distribution, not the
candidate or host gates. If evidence combines an existing exact-source CI run
with separately executed missing constituents, list those commands and results
explicitly; do not claim a new invocation of an aggregate target.

These release gates do not claim an independent security audit, complete
38-scenario public-preview acceptance or production adoption. See
[RELEASING.md](../RELEASING.md) for the separate full-preview program.
