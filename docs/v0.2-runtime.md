# goauth v0.2 Runtime Contract

`goauth` v0.2 exposes a small host-facing Runtime rather than public concrete
repositories and implementation services. PostgreSQL owns canonical auth
state, Redis owns ephemeral OIDC state, and Fiber remains a transport adapter.

## Stable packages

The intended stable import set is:

- `github.com/assurrussa/goauth`
- `github.com/assurrussa/goauth/postgres`
- `github.com/assurrussa/goauth/redis`
- `github.com/assurrussa/goauth/fiber`
- `github.com/assurrussa/goauth/oidc`
- `github.com/assurrussa/goauth/oidc/provider`
- `github.com/assurrussa/goauth/oidc/verifier`
- `github.com/assurrussa/goauth/rbac`
- `github.com/assurrussa/goauth/testkit`

The machine-readable list in `reference/externalconsumer` remains the release
source of truth. The earlier v0.1 implementation remains compile-checked in
`internal/legacy`, which external consumers cannot import. Its published tags
remain immutable; the v0.2 Runtime does not yet replace every old use case.

## Identity and realm model

`Subject` is the canonical security principal. It contains only its canonical
identifier, account status, security version, and timestamps. Identifiers,
basic profile data, local credentials, memberships, and RBAC assignments are
separate records keyed by the canonical subject identifier.

Email is the built-in identifier. Its normalized value is lowercase and unique
per identifier scheme, while its display value preserves the caller-provided
spelling. `user` and `admin` are built-in realms; hosts can register additional
realms. Admin sessions require a verified email and a successful host-owned
membership gate. An unverified user receives only a confirmation-scoped
session.

Suspending or disabling a subject increments its security version and revokes
server-side sessions and refresh families atomically. Offline access tokens
have a maximum lifetime of five minutes.

## Atomic security state

Refresh rotation, password-reset consumption, OIDC authorization state, and
email-challenge verification are single-use operations. Stores return typed
outcomes such as success, invalid, expired, or replayed; they do not expose a
public `Get` followed by `Delete` workflow.

Refresh and reset tokens use a public selector plus an HMAC digest of the
secret. Email challenges store only an HMAC digest. Refresh replay revokes the
whole family. Password-reset consumption, credential update, security-version
increment, and session revocation share one PostgreSQL transaction.

Interactive `Register` creates an unverified account and confirmation-scoped
session. `ProvisionTrustedLocalAccount` is reserved for operator-controlled
seed/bootstrap paths and creates a verified account without an implicit login.
`VerifyCredential` supports recent-authentication checks without bypassing
normalization, throttling, or constant-cost missing-account verification.

Password change uses an exact-PHC compare-and-swap transaction: concurrent
changes using the same old password permit one commit, increment security
version, and revoke local plus OIDC refresh families. Email change is a separate
digest-only challenge with persisted attempts and the same 60-second, 5/hour,
10/day issuance limits. Successful confirmation atomically updates and verifies
the primary email, increments security version, and revokes existing sessions.
`Logout` and `LogoutAll` revoke canonical server-side sessions and refresh
families; profile updates affect only `auth_basic_profiles`.

OIDC offline refresh tokens use the same at-rest rule through the PostgreSQL
adapter: only selector and HMAC digest are stored. Atomic rotation permits one
success; replay revokes the complete OIDC token family and records a typed
security audit event.

Confirmation issuance is append-only and uses atomic rate-limit events. The
defaults are a six-digit code, ten-minute lifetime, five failed attempts,
sixty-second resend delay, five sends per hour, and ten per day. Failed attempt
counters commit before a typed invalid-code result is returned.

## Cryptographic boundaries

JWT signing, token HMAC, and notification-envelope AEAD use distinct versioned
key rings. Runtime construction rejects missing, duplicate, or undersized keys.
Notification payloads containing a raw one-time secret are emitted only as an
AES-256-GCM envelope with a key identifier and random nonce.
The sink contract includes delivery acknowledgement and expiry cleanup, and
the Runtime decrypts only envelopes whose authenticated metadata matches the
event type and canonical subject.

Local passwords are validated server-side with a minimum of 8 and maximum of
128 Unicode code points plus a common-password deny list. They are stored as
versioned Argon2id PHC strings using at least 19 MiB memory, two iterations, and
one lane.

## Schema lifecycle

The v0.2 migration runner installs a clean baseline schema. If it detects the
v0.1 schema, it returns `postgres.ErrLegacySchemaRequiresReset` and makes no
destructive change. Dev/test reset is an explicit, confirmation-gated command;
there is no automatic data deletion or in-place v0.1 conversion.

## Host ownership

Hosts own route prefixes, cookies, redirects, UI, membership tables, profile
extensions, permission catalogs, and notification presentation. Integration is
through `IdentifierResolver`, `MembershipGate`, `ClaimsEnricher`,
`NotificationRenderer`, `URLBuilder`, and `AuditSink` hooks. Host-specific DTOs
are mapped at the adapter boundary and do not enter canonical models.
`ClaimsEnricher` may add namespaced application claims but cannot replace JWT
issuer, subject, audience, lifetime, realm, scope, session, or security-version
claims.

The stable `rbac.Service` exposes hierarchy-free role and permission CRUD,
atomic replacement of role permissions and subject roles, and a consistent
snapshot for host editors and cache rebuilds. It returns canonical RBAC models;
host-specific list, form, and permission-catalog DTOs remain host-owned.
